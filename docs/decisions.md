# Decision log

One line per decision: what, why, and what we gave up. Newest at the bottom. A decision is changed by adding a new row that supersedes the old one, never by editing it.

| ID | Date | Decision | Why | Trade-off / alternative rejected |
| --- | --- | --- | --- | --- |
| D-01 | 2026-10-20 | Python 3.12 via `uv`, FastAPI, open_clip, faiss-cpu; React + Vite + TypeScript; PostHog; pytest, Vitest, Playwright | open_clip loads both models through one API; FastAPI gives typed multipart endpoints with little code; PostHog's free plan has events, feature flags and experiments in one tool | The machine has Python 3.10, so `uv` downloads 3.12 (asked for in the M1 plan). Two languages and two test runners |
| D-02 | 2026-10-20 | Labels from `ashraq/fashion-product-images-small`, images from `ceyda/fashion-products-small`, joined on `id` | The ashraq images are 60 × 80 px, which the models would scale up nearly 4× to their 224 px input, blurring away the pattern and texture that separate one shirt from another. The ceyda copy has the same products at 384 × 512 but no type or colour labels | Two downloads (about 0.9 GB) and a join; products missing from either side are dropped and counted (US-01 AC3). The full-resolution Kaggle set was rejected because it needs a Kaggle login and about 25 GB |
| D-03 | 2026-10-20 | Catalogue = 10 article types (Tshirts, Shirts, Tops, Kurtas, Dresses, Jeans, Trousers, Shorts, Casual Shoes, Handbags), at most 500 each, seed 2026, about 4,960 products. Sarees, Watches and Sunglasses are reserved as out-of-catalogue types | These are things people photograph on themselves and friends. Every type has at least 464 products in the source, so the catalogue stays balanced, and a top-10 list is 0.2% of it, so random ranking scores low (the plan's objection to a 20-product catalogue) | Accessories, socks and underwear are left out. Dresses has only 464, so the catalogue is just under 5,000 |
| D-04 | 2026-10-20 | Compare two models, one index each: OpenCLIP `ViT-B-32` / `laion2b_s34b_b79k` (generic baseline) and `hf-hub:Marqo/marqo-fashionCLIP` (fashion, built on ViT-B-16, Apache 2.0) | One model alone is a demo; the comparison is the experiment, and it puts a number on what a domain model buys | Two indexes to build; the fashion model is about 4× the compute per image (196 patches against 49) |
| D-05 | 2026-10-20 | Exact search: FAISS `IndexFlatIP` on L2-normalised vectors, so inner product equals cosine similarity | 5,000 × 512 floats is about 10 MB, and a full scan takes well under a millisecond on this CPU. An approximate index would add tuning and recall loss for no speed gain; embedding the photo is where latency goes | Revisit above about 100,000 products |
| D-06 | 2026-10-20 | Relevant = same `articleType` and same `baseColour` as the query label, using the source's colour names as written. Type-only is reported beside it | Matches how shoppers are assumed to judge similarity (A1, P5), and a person can check it from labels alone. Strict colour names make the numbers conservative: a `Navy Blue` result for a `Blue` label counts as a miss | Understates quality where colours are near-identical (PRD Q5). Pattern and style aren't captured at all; usability fills that gap |
| D-07 | 2026-10-20 | Query photos are split once into dev (about 30%) and test (about 70%) by seed. The floor, quality thresholds and model choice are tuned on dev only; every test read is logged | With under 100 photos it's easy to overfit choices to the photos you're scoring on. A logged test split keeps the headline number honest | A smaller dev set gives noisier tuning |
| D-08 | 2026-10-20 | Pre-registered model rule: ship FashionCLIP only if its dev Recall@10 (strict) beats OpenCLIP by ≥ 5 points **and** its p95 server latency is ≤ 500 ms; otherwise ship OpenCLIP. Applied by a script (US-06) | Writing the rule before the numbers exist removes the temptation to pick whichever result looks better afterwards. Five points is roughly one extra hit in every 20 photos, small enough to be worth a slower model and large enough to sit outside most of the dev set's noise | A close call can go to the generic model even if the fashion model looks better by eye |
| D-09 | 2026-10-20 | Below a similarity floor, show "No close match" instead of results, with "Show closest anyway". The floor is the highest value that still answers ≥ 90% of in-catalogue dev photos | Junk results cost more trust than no results (P3, A3). Fixing the in-catalogue answer rate first means real searches aren't sacrificed to reject odd ones | Some out-of-catalogue photos will still get results; the rate is reported (PRD §5) |
| D-10 | 2026-10-20 | Several garments in one photo: manual crop in v1, no automatic detection | Detection needs another model, another eval and another latency cost. A crop is one control, and usability task 2 shows whether shoppers find it | One extra step for outfit photos |
| D-11 | 2026-10-20 | The phone resizes the photo to 640 px on its long side and re-encodes it as JPEG before upload | A 12 MP photo is 3–5 MB, which is seconds of upload on a phone network, and the model only uses 224 px. Re-encoding also strips EXIF, including GPS | The server can't be handed a sharper image for any future feature |
| D-12 | 2026-10-20 | Uploaded photos live only in memory for one request; nothing about them is logged or sent to analytics | Photos from a camera roll are personal. ASOS states the same for Style Match (competitive analysis). Nothing kept means nothing to protect | No way to replay a shopper's failed search later; usability notes have to cover that |
| D-13 | 2026-10-20 | Layout A/B test through a PostHog feature flag, with metric, sample size, duration and decision rule written in advance ([ab-test-plan.md](ab-test-plan.md)). If too few searches arrive, the result is reported as directional and the layout decision rests on the usability round | An experiment you can stop when it looks good isn't one. Being upfront about power stops a ten-person test from being sold as proof | A portfolio demo may never reach the sample size; that limit is stated wherever the number appears |
| D-14 | 2026-10-20 | Quality warnings are a banner above the results, never a blocking dialog | A blurry photo often still finds the item; blocking would add a step for every warned search. The banner offers the retake without forcing it | Some shoppers will ignore the banner and blame the search |
| D-15 | 2026-10-20 | Docs are the primary deliverable; stable IDs and a generated traceability matrix, same as the Rental Operations Tracker | A reviewer should get from spec → requirement → story → test → result in under a minute | Upkeep each time a story changes |
| D-16 | 2026-10-20 | The board and bugs live in Jira; the GitHub issue templates mirror the same fields | Jira is what PM roles expect to see; GitHub keeps a public copy reviewers can open | Two places to keep in step; Jira is the source of truth |
| D-17 | 2026-10-20 | CPU-only torch wheels, for the API and for the offline index build | Latency is measured on CPU anyway (NFR-01), the CUDA wheels add about 2 GB, and embedding 10,000 images on 12 threads takes minutes, not hours | The GTX 1650 stays idle. If a rebuild ever gets slow, R-16's fallback still applies |
| D-18 | 2026-10-20 | One branch per feature (`feature/US-nn-…`), merged into `dev` with a merge commit; `dev` merges into `main` at each milestone tag | Each story's tests, code and session log land as one reviewable unit, and `main` only ever holds finished milestones | More merge commits in the history |
| D-19 | 2026-10-20 | Datasets and model weights pinned to Hugging Face commit SHAs, downloaded as files with `huggingface_hub`; no `datasets` library | A dataset or model updated upstream would silently change every number (NFR-03). Reading the parquet files directly is fewer dependencies and keeps the exact bytes | A new upstream version needs a deliberate SHA bump, logged here |
| D-20 | 2026-10-20 | Unit tests run on a small generated fixture (fake products, generated images, a fake embedder); checks on the real 5,000-product build are marked `data` and run with `make test-data` | CI must not download 1.5 GB or load two models on every push, and tests should fail for logic errors, not network ones | A bug that only shows at full scale is caught by `make test-data`, not CI. The milestone review runs it |
| D-21 | 2026-10-20 | Catalogue images are written to `data/images/` as the source JPEG bytes, not re-encoded | Re-encoding would lose quality and make the files differ from the source | Images keep whatever quirks the source has; the size check (US-01 AC3) catches the bad ones |
| D-22 | 2026-10-20 | Accept the catalogue at 4,905 products instead of the "about 4,960" in D-03; no top-up from other types | 956 labelled products have no image in the ceyda copy and 40 images are 150 × 200 thumbnails, so Dresses (437), Trousers (472) and Shorts (496) fall under 500. The smallest type is still 87% of the largest, and a top-10 list is 0.2% of the catalogue either way (R-01) | Slightly uneven types; adding an 11th type or relaxing the size check would change what D-03 and the eval plan describe |
| D-23 | 2026-10-20 | Both models load from a pinned Hugging Face snapshot through open_clip's `local-dir:` loader, not by name (`hf-hub:` or a pretrained tag) | open_clip's `hf-hub:` and pretrained-tag paths download whatever the repo's main branch holds, so a re-upload upstream would change the embeddings without anyone noticing (D-19). The snapshot path takes a revision | Two weight files per model are fetched with `huggingface_hub` directly; open_clip's own cache isn't used |
| D-24 | 2026-10-20 | The index's catalogue check hashes content (id, type, colour, image bytes), not the parquet file | Parquet bytes can differ between library versions for the same rows, which would flag a current index as stale; and a changed image with the same product list would slip past a file-list check | Hashing reads all 4,905 images (115 MB) whenever an index loads, about a second; acceptable for the API's start-up |
| D-25 | 2026-10-20 | Keep the CPU index build (D-17) although it took 46 minutes, not the "minutes, not hours" D-17 expected: 649 s for OpenCLIP and 1,780 s for FashionCLIP on 6 torch threads | It runs once per catalogue change; `make index` now reuses a current index without loading either model, so an unchanged rerun takes under 2 s. The CUDA wheels would add about 2 GB for a step that rarely runs | A catalogue change costs most of an hour. If that starts to happen weekly, revisit (R-16) |
| D-26 | 2026-10-21 | Query photos come from Openverse, limited to CC0, public-domain mark, CC BY and CC BY-SA photographs, each credited in `eval/queries/ATTRIBUTION.md`. Freepik (asked for by the owner) and Pexels were checked and rejected | Freepik, now Magnific, forbids using free content "for any machine learning and/or artificial intelligence purposes" (terms §8.1(7)) and bans automated downloads (§2). Pexels forbids scraping "for machine learning purposes" and using the service "for purposes of performance benchmarking" (terms §8). Openverse has a keyless public API, and those four licences allow any use with credit | The owner's own phone photos were the plan (eval plan §2). Web photos are taken by other people, often better lit and framed than a shopper's quick snap, so the numbers may flatter the search (R-17). NC and ND licences are excluded, so some good photos are skipped |
| D-27 | 2026-10-21 | Each query photo is stored as the phone would send it: cropped to the garment where needed, resized to 640 px on the long side and re-encoded as JPEG, which drops EXIF (D-11). The attribution file says what was changed | Keeps the eval input identical to what `/search` will receive, keeps the repo small, and removes metadata. Cropping is how a face or a second garment is removed (NFR-07) | BY-SA photos are adapted, so the stored files carry BY-SA too; the attribution file says so |
| D-28 | 2026-10-21 | Claude Code labels each query photo's type and colour from the photo alone, using only the catalogue's vocabulary, before any search is run. The owner spot-checks a sample | The owner asked for the build to proceed without their photos, and someone has to label them. Labelling before searching keeps labels from bending toward results | Labels made by the builder, not a shopper, and by an AI model looking at the photo. Colour names are subjective (`Navy Blue` vs `Blue`). The spot-check result goes in OQ-05 |
| D-29 | 2026-10-21 | Dev/test split stratified by article type within in-catalogue photos, never leaving a type under 4 test photos; the first split, assigned minutes earlier by kind only, was cleared once and reassigned | Stratifying by kind alone gave Tops 0 dev and 6 test, and left Kurtas, Shirts and Trousers with 3 test photos each, under the eval plan's minimum of 4. Nothing had read either split (no eval code existed), so changing the rule then cost no bias; after this, AC3 holds: assignments never change | With 5–8 photos per type, dev gets 1–2 per type, so tuning on dev is coarse. Out-of-catalogue and not-fashion photos are still stratified by kind only |
| D-30 | 2026-10-21 | A query photo whose type and colour the catalogue doesn't stock stays in the strict metrics as a miss; the results file counts such queries per split (`unanswerable_strict`) and the per-query file gives each query's number of possible matches | Shoppers photograph what they see, not what the shop holds, so leaving these out would flatter the search. Relabelling the photo to a stocked colour would bend labels toward the catalogue. Counting them keeps the ceiling visible: with one such photo in 44, the best possible strict Recall@10 on test is 43/44 | The headline number mixes "the model missed" with "nothing to find". The per-query file separates them |

# One index per model, 2026-10-20

## What the user needs
The product owner needs both models to search exactly the same products, so the comparison in M2 is about the models and nothing else.

## What the docs said
- FR-11 ([PRD §6.1](../PRD.md#61-functional)): `make index` builds one FAISS index per model in one command.
- US-02 ([user-stories.md](../user-stories.md#us-02-build-one-index-per-model)): AC1 an index, ID file and meta per model; AC2 vectors of length 1; AC3 at least 198 of 200 catalogue images find themselves at rank 1; AC4 an index from a different catalogue is refused with "Index is out of date: run make index".
- D-04 (the two models), D-05 (exact `IndexFlatIP` on normalised vectors), D-17 (CPU only), D-19 (pinned revisions).
- UAT cases TC-CAT-05 to TC-CAT-08.

## Plan
`vsearch/embed.py` wraps both models behind one small interface (`embed(images)` → normalised float32 rows, `describe()`). `vsearch/index.py` builds, loads and checks indexes against that interface, so the tests can pass a fake embedder and never load a model (D-20). `make index` reuses an index that still matches the catalogue, because rebuilding both takes many minutes.

Left out on purpose: search itself beyond the rank-1 check (US-07, M3), and any GPU path (D-17).

Before writing the self-check I checked the catalogue for byte-identical images, since two products sharing one photo would tie at rank 1 and fail AC3 through no fault of the wiring. There are none among the 4,905, so a miss in the check would be a real finding.

## Tests written
Unit tests (`tests/test_index.py`) on the fixture catalogue from US-01, with `FakeEmbedder` in `tests/conftest.py`: a 6-number vector from each image's mean colour and its complement, normalised. Same interface as the real embedder, no model.

- TC-CAT-05: each model gets `vectors.faiss` (an `IndexFlatIP`), `ids.npy` in catalogue order and `meta.json`; and row i of the index equals the embedding of product `ids[i]`, so a hit maps to the right product.
- TC-CAT-06: every stored vector has length 1 within 0.001.
- TC-CAT-07: 20 sampled catalogue images find themselves at rank 1, and the check lists any that don't.
- TC-CAT-08: loading is refused with "Index is out of date: run make index" when the product list changes, and also when only an image file changes.
- No index says "No openclip index: run make index"; no catalogue says "run make catalogue first"; a rerun with current indexes loads no model; `--force` rebuilds both.

Checks on the real build (`tests/test_index_data.py`, `make test-data`): each index loads (so its catalogue hash matches), is aligned with the catalogue, records the pinned revision, has unit-length vectors, and its stored self-check found at least 198 of 200.

First failures: a stub module with `NotImplementedError` made all 9 index tests fail on their own. Before running them I caught a bad assertion in my own test for the missing-catalogue message: it ended in `or True`, so it could never fail. Rewritten to check stderr properly before any code existed.

## What I built
- `vsearch/embed.py`: `MODELS` (both pinned) and `ClipEmbedder`, which downloads the two weight files at the pinned revision and opens them with open_clip's `local-dir:` loader (D-23). Image tower only, CPU, normalised float32 output.
- `vsearch/index.py`: `build_index`, `load_index` (refuses a stale index), `catalogue_hash` (content-based, D-24), `self_retrieval`, and `main` for `make index`.

The real build (output of `make index`):

| | OpenCLIP ViT-B-32 | Marqo-FashionCLIP |
| --- | --- | --- |
| Vectors | 4,905 × 512 | 4,905 × 512 |
| Embedding time, batches of 64, 6 torch threads | 649 s (about 7.6 images/s) | 1,780 s (about 2.8 images/s) |
| Self-check, 200 images embedded afresh | 200 of 200 at rank 1 | 200 of 200 at rank 1 |
| Index size on disk | 9.7 MB | 9.7 MB |

Whole run: 46 minutes wall clock, peak memory 2.6 GB.

This is slower than I expected. D-17 said the CPU build would take "minutes, not hours". 46 minutes is under an hour but not what I meant, so D-25 records the real number and why the CPU build stays.

The throughput gap is an early signal for M3, not a result. FashionCLIP embedded at about 2.7× the time per image of OpenCLIP. That's roughly in line with ViT-B-16 doing 4× the patch work, less fixed costs like image decoding. If single-photo latency follows the same ratio, the fashion model could be the one at risk of the 500 ms budget. That's exactly the trade-off D-08 was written for. R-06's likelihood goes up from 2 to 3 at the M1 risk review. The real numbers come from `make bench` in M3, one photo at a time, which is a different measurement from batch throughput.

## User review
- Main task: get both indexes ready after `make catalogue`, then re-run safely whenever unsure whether they're current.
- Steps: 1 command, `make index`. First run 46 minutes with progress lines every 640 images per model.
- Rerun when nothing changed, before review: 47 s. Both models were loaded and the 200-image self-check re-embedded, even though nothing was rebuilt. After review: 1.7 s, no model loaded, and the stored self-check is reported as "(from the build)". Test first: `test_given_up_to_date_indexes_…_then_no_model_is_loaded`.
- Errors: no catalogue → "No catalogue in data/: run make catalogue first."; no index or a stale one → the message names `make index`. Each says what to run next.
- Remaining friction: the first run's 46 minutes. The progress lines make it bearable but not short. Not fixing it now (D-25).

## Decisions
- D-23 load models from pinned snapshots; D-24 content-based catalogue hash (measured at 0.9–1.1 s); D-25 keep the CPU build.
